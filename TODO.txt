:: 7/26/2026 expression marking notes

We have 2 important features

- debugging and errors with line numbers (obviously)
- mapping from AST to the node graph UI layout should do "best effort" reconstruction to preserve the exiting layout 
- the runtime needs to support partial revals both through input changes an through code changes

in order to do this, we need to be able to give a semi-stale id to each expression allowing it to be mapped back to the UI nodes and the expression thunks in the runtime

hashes can be evaluated for expressions allowing them to be uniquely matched to each other.

note that some annotations affect the hash and some don't. technicalyl the runtime and ui could use different hashes but lets not do this for simplicity

suggest doing this in 2 when running the AST thingy

store the original AST
first pass reconstrucst the AST, expressions that evaluate the same are of coures the same, for expressions that evaluate different, mark them in the original AST as dropped, and mark them in the new ast as new
now do a comparison pass between the old and new, attempting to stitch stuff together where it makes sense according to the set of rules
- new/old matching expressions within the same scopes are stiched together first
- expand the scope by 1 and rerun the stitching algorithm
- contiue, we may have some setof conditions on the scope after which we stop attempting to stitch

note that the UI willalso store these hashse as semi stable ids that do presist betwene open/close. the UI is allowed to store session state but it seems like it's not needed for node stitching.


some additional notes, the UI also serializes an ephemeral state file that prsecribes annotations to expressions via their expression hashes (this is useful for stuff like positions, we don't want to store every position into the file cuz it would bloat it so better to store it as a sidecar file, esp since we don't worry about losing stuff here)
alternatively, the UI can serialize the state directly into the file with special annotations that get dropped in the editor when displaying to the user, but this kind asucks cuz agent has extra shit to parse so no

Knot is a programming language designed for collaborative agentic driven "development" of programmatic designs. 
It is a functional language with a bidirectional mapping so that high level flow and changes can be easily read and modified in a visual format. 
It provides programmable interfaces that allow visually driven changes of the final design to modify constants in source code.
